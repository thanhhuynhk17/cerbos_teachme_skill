Policy trong Postgres: sửa quyền lúc PDP đang chạy

Đưa policy của bài 0001 vào Postgres qua Admin API, sửa / tắt / xoá mà không restart, rồi tự gặp bẫy cache khi chạy nhiều PDP.

Kết quả cần đạt: anh thêm một luật ABAC mới (flagged) vào Cerbos đang chạy chỉ bằng một lần gọi Admin API, và verify.py flagged báo ĐẠT ✓. Đây chính là việc nút Publish trong repo cerbos_payloadcms_ui làm.

0. Ôn lại bài 0001 (không xem lại bài cũ)

Bốn câu ngắn. Cố nhớ lại trước khi chọn; cảm thấy khó là đúng lúc trí nhớ đang được củng cố.

1. Chưa có policy nào cho kind album:object. Kết quả cho comment?
Cerbos mặc định từ chối: không có rule ALLOW nào khớp thì là DENY.
2. Rule có actions: ['*'] có khớp action comment không?
Action là chuỗi tuỳ đặt, không cần khai báo ở đâu trước. '*' khớp tất cả.
3. Trong request, album:object là gì?
Kind quyết định Cerbos dùng resource policy nào (resource: "album:object").
4. Biểu thức CEL nào lấy id của người đang gọi?
id và roles là field có sẵn của principal. attr.* chỉ chứa thuộc tính tuỳ ý anh gửi kèm.

1. Policy có thể nằm ở đâu

Ở bài 0001, PDP đọc policy từ thư mục (driver disk) và tự theo dõi file thay đổi. Cerbos còn nhiều storage driver khác[storage]:

DriverCập nhật policy bằng cáchGhi qua Admin API?
disksửa file (+ watchForChanges)không
git, blob (S3…)commit / upload, PDP poll định kỳkhông
postgres, mysql, sqlite3gọi Admin APIcó
hubCerbos Hub push bundle xuống (mục 6)không

Một dashboard sửa quyền tự host cần hai thứ: một mutable store (Postgres) và Admin API được bật.

Admin API đi đường nào

Dashboard / admin.py ──POST /admin/policy (basic auth)──► PDP ──ghi──► Postgres (bảng cerbos.policy)
                                                          │
                                                          └─ cập nhật CACHE của chính PDP này
App ──CheckResources──► PDP (đọc từ cache)

Hai điều cần nhớ, lấy từ docs[storage, mục Postgres][admin_api]:

  1. PDP giữ policy đã compile trong cache bộ nhớ. Khi ghi qua Admin API, chính PDP nhận request cập nhật cache của nó ngay. Không có bước "theo dõi file" nào cả.
  2. Admin API bắt buộc đăng nhập (basic auth, một tài khoản admin duy nhất). Không cấu hình thì tài khoản mặc định là cerbos / cerbosAdmin. Lab dùng tài khoản mặc định này; môi trường thật phải đổi mật khẩu và bật TLS.

3. Bước A: database trống

Dự đoán: uv run verify.py deny-all trên PDP mới (Postgres chưa có dòng nào) sẽ ĐẠT hay CHƯA ĐẠT? Vì sao?

ĐẠT. Bảng cerbos.policy trống, nên không có resource policy cho album:object, và mọi action bị DENY theo mặc định. Đổi nơi lưu policy không làm đổi quy tắc đánh giá.

uv run admin.py list            # → {} : chưa có policy
uv run verify.py deny-all

4. Bước B: đẩy policy, sửa, tắt

B1. Đẩy hai file YAML của bài 0001

admin.py put đọc các file YAML, đổi thành JSON rồi gửi POST /admin/policy với body {"policies": [...]}. Repo của anh làm đúng việc này trong src/cerbos/admin.ts.

Dự đoán: ngay sau put, có cần sleep 3 như bài 0001 thì verify.py challenge mới ĐẠT không? Dựa vào điều nào ở mục 1?

Không cần chờ. Ở bài 0001, PDP phải phát hiện file đổi (watch) nên mất khoảng 3 giây. Còn ở đây, Admin API ghi thẳng vào PDP, và PDP cập nhật cache của chính nó ngay khi xử lý request (điều 1, mục 1). Khi em chạy thử, verify ĐẠT ngay lần gọi đầu tiên.

uv run admin.py put policies/
uv run admin.py list            # → derived_roles.common_roles, resource.album_object.vdefault
uv run verify.py challenge
./pgstore/psql.sh -c "select id, kind, name, version, disabled from policy;"

Để ý policy ID: resource.album_object.vdefault, tức là resource. + kind (dấu : đổi thành _) + .v + version. Các lệnh get/disable/delete đều dùng ID này. Cột definition là BYTEA, nên đừng sửa policy bằng SQL; chỉ ghi qua Admin API.

B2. Sửa một rule

Mở policies/resource_album.yaml, đổi rule thứ hai về như cũ là actions: ['view:public'] (bỏ comment), rồi đẩy lại.

Dự đoán: sau khi đẩy lại, bước nào của verify.py sẽ ĐẠT: owner, public hay challenge?

public. Đây chính là policy ở Bước C của bài 0001: DAFFY002 xem được nhưng không comment được. POST /admin/policy vừa thêm vừa cập nhật theo policy ID.

uv run admin.py put policies/resource_album.yaml
uv run verify.py public
./pgstore/psql.sh -c "select revision_id, action, name, disabled, update_timestamp from policy_revision order by 1;"

Bảng policy_revision do trigger trong schema.sql ghi lại: mỗi lần thêm, sửa hay tắt policy đều thêm một dòng. Anh có sẵn audit trail ở tầng DB mà không phải viết thêm code.

B3. Tắt và bật lại

Dự đoán: uv run admin.py disable resource.album_object.vdefault xong thì verify.py bước nào ĐẠT? Áp dụng bước nào trong "4 bước đánh giá" của bài 0001?

deny-all. Policy bị disable coi như không tồn tại, nên bước 1 (tìm resource policy cho kind) thất bại và mọi action bị DENY, kể cả quyền của owner. Derived roles vẫn còn, nhưng không còn rule nào dùng tới.

uv run admin.py disable resource.album_object.vdefault
uv run verify.py deny-all
uv run admin.py list            # không thấy nữa
uv run admin.py list --all      # vẫn còn trong store, ở trạng thái disabled
uv run admin.py enable resource.album_object.vdefault

B4. Xoá thứ đang được dùng

Bảng policy_dependency ghi lại policy nào import policy nào. Ở đây resource.album_object.vdefault import derived_roles.common_roles.

Dự đoán: uv run admin.py delete derived_roles.common_roles sẽ thế nào? (a) xoá được, owner mất quyền; (b) xoá được, không ảnh hưởng gì; (c) bị từ chối.

(c) Bị từ chối: HTTP 400 kèm requiredByOtherPolicies, có liệt kê resource.album_object.vdefault. Cerbos không cho tạo ra trạng thái hỏng. Muốn xoá thì phải xoá hoặc sửa policy phụ thuộc trước.

uv run admin.py delete derived_roles.common_roles

disable giữ policy lại để bật sau; delete xoá hẳn. Endpoint cũ DELETE /admin/policy?id= đã deprecated và thực chất chỉ disable[admin_api]. Test harness của repo anh (test/harness/cerbos.ts:34) đang dùng endpoint này. Vì vậy trong store dev của repo có các policy invoice/plan/report ở trạng thái disabled (em kiểm tra chỉ đọc qua GET /admin/policies?includeDisabled=true).

5. Bước C: hai PDP, một database

Muốn tải cao thì chạy nhiều PDP (replica) cùng đọc một Postgres. Bật thêm replica ở cổng 4594:

(cd pgstore && docker compose --profile replica up -d --wait)
CERBOS_HOST=http://localhost:4594 uv run verify.py public   # replica thấy cùng dữ liệu: ĐẠT

Giờ đẩy lại bản challenge (thêm comment vào rule thứ hai như cũ) qua PDP 4592:

# sửa policies/resource_album.yaml: actions: ['view:public', 'comment']
uv run admin.py put policies/resource_album.yaml     # gửi tới 4592
uv run verify.py challenge                           # 4592
Dự đoán: CERBOS_HOST=http://localhost:4594 uv run verify.py challenge (replica) sẽ ĐẠT hay CHƯA? Dựa vào điều 1 ở mục 1.

CHƯA ĐẠT. Chỉ PDP nhận request (4592) cập nhật cache. Replica 4594 vẫn dùng policy cũ trong bộ nhớ dù database đã có bản mới. Em đã tái hiện đúng hiện tượng này trong lab. Docs đưa ra hai cách[storage, mục Postgres]: gọi /admin/store/reload trên mọi PDP sau mỗi lần publish, hoặc đặt compile.cacheDuration để cache tự hết hạn (các PDP dần dần nhất quán).

CERBOS_HOST=http://localhost:4594 uv run verify.py challenge
CERBOS_ADMIN_HOST=http://localhost:4594 uv run admin.py reload
CERBOS_HOST=http://localhost:4594 uv run verify.py challenge     # giờ ĐẠT
(cd pgstore && docker compose --profile replica stop cerbos-replica)

Đây là câu trả lời cho câu hỏi ADR-0003 trong repo của anh còn để ngỏ: "How multiple replicas pick up new policies is unverified".

6. Liên hệ với repo và Cerbos Hub

Repo cerbos_payloadcms_ui

Operator ─UI /matrix─► Payload (nguồn sự thật) ─snapshot → compile()─► POST /admin/policy ─► PDP ⇄ Postgres "cerbos"

Những gì anh vừa làm bằng admin.py chính là bước cuối trong chuỗi trên. Đối chiếu với lab, có hai điểm cần sửa khi đưa vào thật:

  • Policy mồ côi: compile() chỉ sinh policy cho resource đang có, và publish chỉ POST. Xoá một resource khỏi catalog thì policy cũ vẫn còn trong store và vẫn ALLOW. Khi publish cần so với admin.py list rồi disable/delete phần thừa. (Em suy ra từ mã nguồn, chưa chạy thử trên repo.)
  • Nhiều replica: publish phải gọi reload tới mọi PDP, hoặc đặt compile.cacheDuration (mục 5).

Cerbos Hub (trả phí)

Hub là control plane tuỳ chọn; PDP vẫn là binary mã nguồn mở chạy trên hạ tầng của anh[hub]. Policy được đưa vào policy store qua Git, CI, Hub SDK/API, cerbosctl hub store hoặc upload trên trình duyệt[policy-stores]. Mỗi thay đổi kích hoạt một lần build (compile + chạy test), rồi Hub push bundle xuống mọi PDP, nên không cần tự reload từng PDP[deployments]. Hub còn có playground soạn policy kiểu IDE, màn hình Effect matrix (chỉ để xem), và audit log tập trung. Gói miễn phí "Proof of Concept" cho 100 MAP; Development từ $25/tháng; Production từ $933/tháng[pricing].

Trên các trang em đọc không thấy trình chỉnh ma trận quyền kiểu no-code cho operator, như UI /matrix của repo anh. Vì vậy Hub không thay được UI đó. Nó có thể thay phần "Postgres + Admin API + tự reload". So sánh đầy đủ ở research/0001.

7. Kiểm tra

5. Admin API ghi được policy khi PDP dùng driver nào?
Chỉ các mutable store (postgres, mysql, sqlite3) mới nhận ghi qua Admin API.
6. Muốn chặn tạm một policy nhưng vẫn giữ lại để bật sau?
Disable giữ policy trong store (list --all vẫn thấy); enable là có lại ngay.
7. Ba PDP dùng chung Postgres. Cách chính thức nào giúp cả ba thấy ngay bản publish mới?
/admin/store/reload trên từng PDP. Nếu chấp nhận nhất quán dần dần thì dùng compile.cacheDuration.

8. Thử thách: luật ABAC mới, áp dụng khi PDP đang chạy

Trong fixtures.py có album mới DAFFY_FLAGGED: của Daffy, public: true, nhưng flagged: true (bị báo cáo nội dung). Yêu cầu nghiệp vụ: album bị flagged vẫn xem được, nhưng không ai ngoài chủ được comment. Các album khác giữ nguyên như bản challenge.

  1. Sửa policies/resource_album.yaml.
  2. Đẩy lên bằng uv run admin.py put policies/resource_album.yaml. Không restart PDP.
  3. uv run verify.py flagged phải ĐẠT cả 8 dòng.
Gợi ý (chỉ mở khi bí)

Một rule có thể chỉ dành cho comment. Một condition có thể ghép nhiều biểu thức: match: { all: { of: [ {expr: …}, {expr: …} ] } }[conditions]. Thuộc tính nằm ở request.resource.attr.flagged.

Xong thì tắt lab: ./pgstore/down.sh (thêm --reset nếu muốn xoá sạch dữ liệu Postgres).

Nguồn chính

Đọc mục Postgres driver trong Storage drivers (đặc biệt đoạn về cache giữa nhiều instance), sau đó đọc Admin API. Bản tra nhanh ở cheat sheet.
